# CyberBrain v0.2.0 Release — 2026-09-09

> Historical release record. Current operational guidance lives in the non-history docs/specs.

## Release intent

v0.2.0 packages the completed Level-8 source line for deployment **before** the full schema-V2 corpus migration and evaluation gate.

The release deliberately separates software deployment from data migration:

```text
software/runtime release first
→ keep current V1 stage collections readable
→ stage/validate V2 corpus later
→ real M6/M7 evaluation
→ explicit production data cutover only after owner review
```

## Software included

- M3 Salience / Priority;
- M4 Concept Formation / Abstraction;
- M5 Working Memory / Active Context;
- P3.1 trusted-agent identity seam;
- M6 Agent Self-Model source pipeline with fail-closed readiness and accepted-only persistence boundary;
- M7 reversible Memory Lifecycle source pipeline;
- canonical schema-V2 models and migration quarantine semantics;
- full four-source-union V2 staging and independent validation tooling;
- vector-aware migration convergence and exact target-count convergence hardening;
- canonical V2 migration runbook and deployment-neutral canary example.

## Backward-compatible API boundary

The MCP contract remains backward-compatible. Canonical tools remain available, including exact fetch and cognition surfaces, and the legacy aliases remain connected to the same canonical services:

```text
tech_store
tech_find
ai_memory_read
conversation_save
conversation_recall
```

There is no second legacy persistence implementation.

The provider advertises schema version 2 independently from MCP contract version 1.

## Pre-migration recall compatibility

The live deployment may continue reading canonical V1 stage collections before V2 migration. Ordinary recall treats missing V2-only `record_class` / `ordinary_recall` fields as legacy-compatible. Explicit V2 values remain authoritative, so Self-Model hypotheses, migration quarantine, or other explicitly non-recallable rows remain excluded.

This compatibility branch was checked read-only against the live V1 stage collections before release.

## Release gate

Before tagging:

- compatibility/catalog tests pass;
- full regression passes;
- Ruff passes;
- `git diff --check` passes;
- package version is derived from `cyberbrain/_version.py`;
- provider `help` reports the canonical software/schema/contract identities without conflating them;
- local release image builds and reports the release package version.

## Deployment boundary

The v0.2.0 software rollout updates all CyberBrain application services to one image version while retaining the existing V1 stage collection configuration. It does not perform Qdrant schema migration or enable multi-user mode.

Post-deploy checks are limited to release/runtime compatibility smoke; corpus migration, full quality verification, and Level-8.5+ scoring remain subsequent owner-directed gates.

## Deployment result

The release was pushed, tagged, published, and rolled out to all five CyberBrain application services from the same release image. The core provider, Reasoner, Dream router, Dream worker, and Dream scheduler all report the release package version; health/readiness and service health checks passed.

The live collection configuration deliberately remained on the existing V1 stage pair. No Qdrant V2 staging, migration, cutover, re-embedding, or multi-user activation was performed as part of the software rollout.

Direct MCP smoke confirmed:

```text
24 tools advertised
provider version = release version
contract version = 1
schema version = 2
canonical Knowledge recall reads V1 stage
canonical Episodic recall reads V1 stage
tech_find reads successfully with its legacy signature
ai_memory_read reads successfully
conversation_recall reads successfully
tech_store / conversation_save legacy schemas remain advertised
```

The legacy aliases therefore remain adapters into the canonical service paths; no second API/persistence implementation was introduced.
